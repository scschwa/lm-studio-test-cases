Local models as a practical development tool

Seven working examples with LM Studio and Ornith 1.0 9B

LM Studio Test Cases

The useful question is where local inference fits

Local models are most useful when the work is frequent, bounded, measurable, and safe to verify in ordinary code.

Developer request → Local model → Deterministic validation → Artifact or escalation

  • Save time: automate repetitive first passes during development.
  • Control spend: reserve hosted calls for cases that need them.
  • Keep boundaries clear: the model proposes; trusted code validates and acts.

Example 1 starts with one explicit request

Problem and purpose

The first exercise needed a low-frills Python submission that sends one prompt to Ornith and returns a reusable payload instead of starting a chat loop.

completion = client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": PROMPT}],
    temperature=0.2,
)
return {
    "request": {"model": MODEL, "prompt": PROMPT},
    "response": {
        "content": choice.message.content,
        "finish_reason": choice.finish_reason,
        "usage": usage.model_dump(),
    },
}

Example 2 turns stateless calls into a conversation

Problem and purpose

The terminal app needed back-and-forth chat without adding a database, framework, or graphical interface.

messages = [
    {"role": "system", "content": SYSTEM_PROMPT}
]

messages.append({"role": "user", "content": user_text})
assistant_text = request_reply(client, messages)
messages.append(
    {"role": "assistant", "content": assistant_text}
)

The API does not remember earlier requests. Resending the accumulated list is what gives the model conversational context.

Example 2 proves that history is carried forward

You: Reply with exactly the word BLUE.
Ornith: BLUE

You: What word did I ask you to reply with?
     Reply with only that word.
Ornith: BLUE

The two-turn smoke test confirmed that the second request included the first user message and assistant response.

  • History exists only in memory and disappears when the process ends.
  • Every turn resends prior messages, increasing context size and processing time.
  • exit, quit, Ctrl+C, and EOF end the session cleanly.

Example 4 generates tests without executing model code

Problem and purpose

Developers need edge-case ideas, but directly executing arbitrary generated Python adds unnecessary risk. Ornith generates test data; trusted functions run it.

def execute_case(test_case, buggy_function,
                 reference_function):
    args = test_case.get("args", [])
    expected = test_case.get("expected")

    reference_result = reference_function(*args)
    buggy_result = buggy_function(*args)

    return {
        "expected_is_correct": expected == reference_result,
        "detects_bug": buggy_result != expected,
    }

Example 5 keeps tool execution under application control

Problem and purpose

The benchmark asks whether Ornith can choose a tool and construct arguments. The model requests an action; an explicit allowlist decides what may run.

TOOL_FUNCTIONS = {
    "lookup_issue": lookup_issue,
    "run_test_file": run_test_file,
    "calculate_shipping": calculate_shipping,
}

function = TOOL_FUNCTIONS.get(call["name"])
if function is not None:
    result = function(**call["arguments"])

Tool schemas describe parameters, while the Python dispatch table remains the security boundary.

Example 6 uses policy to decide when local is enough

Problem and purpose

A local model can reduce hosted usage even when it is not trusted for every case. The application, rather than the model alone, owns the routing policy.

if assessment["category"] in ALWAYS_ESCALATE_CATEGORIES:
    reasons.append("always-escalate category")
if assessment["confidence"] < 0.80:
    reasons.append("confidence below threshold")
if assessment["requires_expert_review"]:
    reasons.append("expert review requested")

selected_backend = "hosted" if reasons else "local"

Security, financial, and architectural work always escalates.

Start small, measure, then decide what to route

  1. Choose bounded work with a clear input and expected output shape.
  2. Record evidence such as latency, usage, validity, and task score.
  3. Validate in code before generated content changes anything important.
  4. Escalate by policy when risk, uncertainty, or complexity is high.
